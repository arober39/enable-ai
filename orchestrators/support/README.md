# Support Orchestrator

Generated by the **Support Enablement Agent** from the enablement plan dated `2026-09-23T00:00:00+00:00`.

This directory contains the runtime support orchestrator for Serenia & Co. It handles inbound customer support inquiries against Serenia's stack of Intercom, Zendesk, Slack, and HubSpot, fetches its system prompt at runtime from the `support-orchestrator-config` AI Config in LaunchDarkly, and emits the three signals the multi-signal guardrails tutorial monitors.

## Plan summary

Serenia & Co.'s support stack (Intercom, Zendesk, Slack, HubSpot) has strong native AI coverage for first-response drafting and FAQ retrieval, but those capabilities are siloed within each tool and cannot see cross-system context — meaning Intercom's Fin drafts without knowing the customer's plan tier from HubSpot, and Zendesk's triage classifies without knowing whether the customer has open escalation history. The critical gap is escalation routing: no tool in the stack makes a multi-signal routing decision that combines CRM context, ticket content, sentiment, and policy thresholds. The recommended architecture is a custom orchestrator (already generated under orchestrators/support/) that sequences intent classification, Zendesk KB search, HubSpot CRM context lookup, policy-grounded response drafting, and Slack escalation handoff. Intercom, Zendesk, and Slack all have available MCP servers; HubSpot requires a generated stub (already in place at orchestrators/support/mcp_servers/hubspot/). The orchestrator uses LaunchDarkly AI Configs for guarded prompt rollouts and emits support.escalation and support.error events for the multi-signal guardrails tutorial. Zendesk and Intercom have overlapping FAQ retrieval and conversation summarization features — the orchestrator deduplicates by routing FAQ-class tickets through Zendesk KB search via MCP and using Intercom only for the reply-posting step. Native sentiment analysis in Zendesk's Intelligent Triage is sufficient for the basic signal; custom augmentation is not warranted unless escalation thresholds need to be tuned by fine-grained sentiment score, which is a phase-2 concern.

## What it does

When invoked with a customer inquiry it:

1. Builds a LaunchDarkly request-scoped context.
2. Fetches the active AI Config variation (`v1-baseline` or `v2-detailed-responses`).
3. Classifies the inquiry's intent: `FAQ`, `REFUND`, `ESCALATION`, `STATUS`, or `OTHER`.
4. Routes to the right skill (knowledge-base search, policy-grounded refund drafting, structured escalation handoff, status acknowledgment).
5. Returns a structured response: `{intent, draft_reply, confidence, action_taken, citations, escalated, error}`.
6. Emits two LaunchDarkly events:
   - `support.escalation` — `metric_value=1` if escalated, else `0`.
   - `support.error` — `metric_value=1` on error paths only.
7. Emits OTel spans at every step (see `observability.py`).

## Run it

```bash
# From repo root:
cp orchestrators/support/.env.example orchestrators/support/.env
# Fill in keys you have. Without ANTHROPIC_API_KEY and LAUNCHDARKLY_SDK_KEY,
# the orchestrator runs in stub-only demo mode — useful for tests and demos.

make -C orchestrators/support run
```

The default invocation runs against a built-in sample inquiry. To integrate into a real pipeline, import `handle_inquiry` from `orchestrators.support.orchestrator` and pass your own `Inquiry`.

## Tutorial reference

This orchestrator is the demo asset for `tutorial-01-multi-signal-guardrails`. The two variation prompts (`prompts/v1_baseline.md` and `prompts/v2_detailed_responses.md`) differ by one instruction; the tutorial walks through how a single-signal guarded rollout misses the regression that instruction causes, and how attaching a factual-accuracy judge (`judges/factual_accuracy.md`) catches it.

Do not change the prompt files, the AI Config name (`support-orchestrator-config`), the model (`claude-sonnet-4-6`), or the event names (`support.escalation`, `support.error`) without coordinating with the tutorial branch.
